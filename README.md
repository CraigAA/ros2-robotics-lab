# ros2-robotics-lab

> **Work in progress.** A personal lab for learning ROS 2 on real hardware, built around a containerised telemetry stack that runs on a Jetson, a Raspberry Pi and an x86 desktop. Anything marked "planned" is not built yet.

## What this is

A ROS 2 (Jazzy) system that publishes CPU, RAM, GPU and temperature data from several Linux machines and will stream it to a browser dashboard. The same multi-arch Docker image runs on every device. Later phases add simulation and a command-validation layer for safe robot control.

## Architecture (target)

```
[Jetson AGX Orin] hw_monitor ─┐
[Raspberry Pi]    hw_monitor ─┼─ DDS (Cyclone, unicast peers over Tailscale)
[Arch desktop]    hw_monitor ─┘             │
                                            ▼
                              rosbridge_websocket (:9090)
                                            ▼
                                 HTML dashboard (roslibjs)
```

Each node publishes JSON on `/<host>/stats` with sensor-data QoS (best effort), so the dashboard can discover devices from topic names.

## Quick start (monitor)

```bash
cd monitor
docker compose up --build
```

In a second terminal:

```bash
docker exec -it hwmon /ros_entrypoint.sh ros2 topic list
docker exec -it hwmon /ros_entrypoint.sh ros2 topic echo /<host>/stats --once --full-length
docker exec -it hwmon /ros_entrypoint.sh ros2 topic hz /<host>/stats
```

Set the topic name per device with `-p host:=jetson`. Change the rate with `-p rate_hz:=5.0`.

## Design decisions

- **Docker with `--network host`:** DDS discovery does not work through Docker's default bridge network.
- **Multi-arch image:** one Dockerfile based on `ros:jazzy` targets amd64 and arm64.
- **Best-effort QoS:** dropping a 1 Hz stats sample is harmless, and this keeps publishers lightweight.
- **Cyclone DDS with unicast peers:** Tailscale does not carry multicast, so discovery uses an explicit peer list generated from `tailscale status --json`.
- **One collector per platform:** missing hardware (for example no GPU on the Pi) returns `null` instead of failing.
- **rosbridge for the dashboard:** the browser subscribes directly over WebSocket, so no backend code is needed.

## Known limitations

- Stats are published as JSON in a `std_msgs/String`. A typed message is planned.
- rosbridge has no authentication by default, so keep it on the tailnet or LAN only.
- The simulation folders contain installation notes and demo runs only, not original work yet.
